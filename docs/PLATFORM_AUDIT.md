## 1. الملخّص التنفيذي

المشروع أساس هندسي جيد: فصل صريح بين الواجهة والمحرك وقاعدة المعرفة، تحقق مزدوج،
اختبارات حقيقية، رؤوس أمان، ولا تخزين لبيانات المرضى. التوسّع إلى منصة متعددة اللغات
لا يحتاج إعادة كتابة، بل **طبقات إضافية** فوق البنية الحالية.

أخطر فجوة ليست تقنية بل **حوكمية**: 24 حالة وقواعد جرعات وأدوية تُعرض بثقة بصرية عالية
دون أي بيانات مراجعة أو مصادر أو سجل توقيع طبيب. أُغلقت اليوم هذه الفجوة هيكلياً
(بيانات المراجعة، تحقق يمنع الادعاء الكاذب بالاعتماد، وإظهار الحدود للمستخدم)، لكن
**المراجعة الطبية نفسها لم تحدث ولا يمكن للوكيل تنفيذها**.

## 3. تقييم البنية

**نقاط القوة**

- `Disease` كنموذج بيانات واحد، و`knowledge-base.ts` يمنع الأخطاء عند بدء التشغيل.
- `shared/types.ts` عقد واحد للطرفين، والمحرك نقي (بلا I/O) ولذلك قابل للاختبار وإعادة
  الاستخدام في المتصفح.
- الواجهة تفصل العرض عن الحساب، والـ API بلا حالة ولا يخزّن شيئاً.
- وجود مسارين (API وثابت) يعطيان مرونة نشر حقيقية.

**قيود بنيوية تعيق الأهداف**

1. **نموذج سريري فقير:** لا وجود لتعريف الحالة، العلامات السريرية المنفصلة عن الأعراض،
   التشخيصات التفاضلية المرجعية، معايير الإحالة/القبول، خطة المتابعة، أو بنية الأدوية
   القابلة للفحص. النصوص الحرة لا تصلح لبناء P1–P4 أو تقارير أو ترجمة متسقة.
2. **حدود الترجمة:** الواجهة العامة مترجمة، لكن **كل المحتوى الطبي** (أسماء الحالات
   والأعراض والتخصصات، الملخصات، الفحوصات، الإجراءات، التحذيرات، أسباب الفرز،
   والأدوية) عربي فقط ويُعرض مع إشعار صريح. أُزيلت الترجمات الفرنسية السابقة
   للمصطلحات من العرض لأنها غير مُراجعة. ترجمة المحتوى تحتاج مراجعاً طبياً لكل نص
   وحقول اعتماد مرتبطة بالحالة.
3. **التخصصات ناقصة:** 11 تخصصاً فقط، لا تشمل النساء والتوليد، الأطفال، الدم، الروماتيزم،
   الجلدية، السموم، الأمراض المعدية، الكلى كهوية مستقلة.
4. **الملف الواحد ضخم:** `cardio-respiratory.ts` يجمع 8 حالات ونصوصاً طويلة؛ لا يمنع
   التوسّع لكنه يبطئ المراجعة الطبية والتغييرات.
5. **لا إصدار مخطط/هجرة:** أُضيف `schemaVersion` اليوم، لكن لا توجد أداة تحقق من توافق
   نسخة القاعدة مع المحرك.
6. **اختبارات الواجهة جزئية:** أُضيف Vitest + jsdom + Testing Library لاختبار تبديل
   اللغة/RTL وبوابات السلامة، لكن لا توجد اختبارات E2E ولا تغطية لكل مكوّن.

## 5. تحليل الفجوات الأمنية

**موجود وجيد:** Helmet + CSP، منع التضمين، `X-Powered-By` مخفي، rate-limit، رفض
الكتابة عبر الأصول، تحقق صارم يرفض الحقول الزائدة، حدود حجم، عدم تسجيل بيانات،
`no-store`، ولا أسرار في المستودع.

**فجوات يجب معالجتها قبل أي استخدام مؤسسي:**

1. **لا مصادقة/تفويض** — مقصود للنسخة التعليمية، لكنه مانع للاستخدام السريري.
2. **لا سجل تدقيق** — لا يمكن إثبات من رأى/قيّم ماذا.
3. **حدّ المعدل في الذاكرة** — لا يعمل عبر عدة نسخ؛ يحتاج مخزناً مشتركاً.
4. **CSP تسمح `style-src 'unsafe-inline'`** — مقبول لـ Tailwind، ويُستحسن nonce لاحقاً.
5. **لا فحص تبعيات/أسرار في CI** — `npm audit` يدوي؛ يُضاف إلى السير عمل.
6. **النسخة الثابتة تكشف قاعدة المعرفة كاملة** — مقبول لأنها غير سرية، لكن يجب ألا
   تحتوي لاحقاً أي بيانات مرضى أو مفاتيح.
7. **لا حماية من إساءة الاستخدام/DoS على المستوى التطبيقي** — rate-limit فقط.
8. **الامتثال:** أي نشر جزائري يتطلب تقييماً لحماية المعطيات الشخصية ووضع الجهاز الطبي؛
   لا يُدّعى الامتثال حالياً.

## 6. الدين التقني

- الكتالوج يعيد `labelAr`/`labelEn`، لكن العرض يفرض العربية للمحتوى الطبي.
  لا توجد ترجمة سريرية معتمدة، ولا توجد حقول اعتماد مرتبطة بالترجمة بعد.
- **حزمة GitHub Pages تحتوي قاعدة المعرفة كاملة**، ومنها بيانات أدوية، رغم حجب
  العرض والـ API. القرار المعتمد مؤقتاً: إبقاء البيانات في الحزمة الثابتة وعدم حذف
  الكود أو نقل الحساب إلى خادم خارجي، إلى حين المراجعة الطبية (القسم 12).
- إعداد `LanguageProvider` يغيّر `document.dir` عند التشغيل؛ لا توجد نسخة SSR.
- وزن/حدود العلامات مكرّرة بين `shared/types` و`client/lib/form.ts` (مصدران للحقيقة).
- `ENGINE_VERSION` ثابت يدوياً؛ لا Changelog للقاعدة.
- `DISEASE_COURSE` جدول منفصل يجب تحديثه يدوياً لكل حالة جديدة (مقصود للتحقق، لكنه
  قابل للدمج في `Disease`).
- لا تنسيق/ESLint في CI (TypeScript فقط).
- لا اختبارات للمكوّنات أو إمكانية الوصول.

### ما أُنجز فعلياً اليوم — المرحلة 3 (i18n) وبوابات السلامة

**البنية:**

- `client/src/i18n/translations/{ar,fr,en}.ts`: قواميس واجهة مركزية، والعربية مرجع
  يفرض TypeScript تطابق المفاتيح في اللغتين الأخريين.
- `client/src/i18n/index.tsx`: `LanguageProvider` + `useI18n` + `t()` مع تعويض
  المتغيرات، تخزين التفضيل، اكتشاف لغة المتصفح، وضبط `html.lang`/`html.dir`
  (`ar` → RTL، `fr/en` → LTR). تنسيق التواريخ والمدة حسب اللغة.
- `client/src/i18n/clinical.ts`: سياسة **العربية فقط** للمحتوى الطبي. أسماء الحالات
  والأعراض والمجموعات والتخصصات والعلامات الحيوية تُعرض من المصدر العربي في اللغات
  الثلاث؛ وحدات المدة فقط تُترجم لأنها نص واجهة. أُزيلت خرائط الترجمة الفرنسية
  غير المُعتمدة. المعرّفات (`acute_coronary_syndrome`…) لم تتغير.
- `Header` فيه مبدّل لغة، وكل النصوص المرئية في الصفحة/النموذج/النتائج/التذييل
  صارت من القواميس. مكوّنات التحقق والأخطاء محلية أيضاً.

**سياسة المحتوى الطبي:** لا تُترجم أسماء الحالات أو الأعراض أو التخصصات أو
الملخصات أو الفحوصات أو الإجراءات أو التحذيرات أو أسباب الفرز أو الأدوية. في FR/EN
يظهر إشعار صريح بأن المحتوى الطبي بالعربية فقط حتى اعتماد ترجمة مُراجعة.

**بوابات السلامة:**

- **الأطفال:** عند العمر < 16 يعيد المحرك `differentials: []` و
  `meta.pediatricUnsupported = true` مع رسالة صريحة؛ لا تُعرض توصيات أو جرعات
  للبالغين. قواعد التسجيل والأوزان لم تُعدّل.
- **الأدوية:** طالما القاعدة غير مُراجعة (`clinicalReviewRequired`) يُضبط
  `meta.medicationContentHidden = true`، وتُفرَّغ `actions.medications` **على مستوى
  الـ API** فلا تعود أسماء الأدوية ولا الجرعات في الاستجابة أصلاً، وتستبدل الواجهة
  القسم بإشعار «المحتوى الدوائي محجوب». لا يوجد أي مسار لعرض الجرعات في هذه الحالة.

**الاختبارات:** 84 اختباراً، منها 9 لواجهة i18n (تطابق القواميس، التعويض، تنسيق
التواريخ، اكتشاف اللغة، RTL/LTR، تبديل اللغة فعلياً عبر المبدّل) و3 لبوابات
السلامة (حجب الدواء، عدم ظهور الاسم، منع توصيات البالغين للطفل)، واختبار يثبت
أن **كل الحالات الـ24** قابلة للوصول بمعطياتها الموثقة. `typecheck` و`build`
و`build:pages` ناجحة، وتحقّق بصري على النسخة الحية باللغات الثلاث. أُضيفت 7 اختبارات للبنية المستقبلية واختبار API لقدراتها، ثم 28 حالة انحدار و3 اختبارات للأمثلة السريعة؛ كلها ناجحة.

## 8. قرارات معمارية منفذة

1. **هوية مستقلة عن اللغة:** المعرّفات إنجليزية وثابتة، والمحتوى الطبي يُعرض من
   المصدر العربي؛ لا تُستخدم الترجمة لتغيير أي معرّف أو قاعدة.
2. **مغلف إجراء مهيكل:** `GovernedClinicalAction` يحمل `id`، حاوية أولوية P1–P4،
   `type`، عنواناً ونصاً مبرراً اختياريين، مراجع، وبيانات مراجعة. لا يحمل تعريفاً
   سريرياً للأولوية (`priorityDefinition` يبقى `pending_medical_definition`).
3. **`Disease.review`** يبقى مصدر حالة الحالة الحالية، ويُمنع `approved` بلا مراجع
   وتاريخ ومصدر. لا ترحيل قسري إلى 3.0 في هذه المرحلة.
4. **حزمة مراجع منفصلة:** مخطط `GovernedReference` مع رابط/مقطع/سنة، وربط بالمعرّفات
   لا بنسخ النصوص.
5. **الحساب يبقى حتمياً:** لا نماذج لغوية في مسار القرار، وأي وحدة مستقبلية تبقى
   معطلة حتى وصول محتوى مُراجع.

## 9. ما ينتظر مراجعة الطبيب (لا يمكن للوكيل إنجازه)

- اعتماد أي حالة من الـ24 (`review.status = approved`) بعد التحقق من المحتوى والمصادر.
- مراجعة جرعات الأدوية وحدودها (الأسبرين، الأدرينالين، السوائل، المضادات).
- التحقق من عتبات الفرز وEWS مقابل سياسة المؤسسة.
- قرار اعتماد مسار جزائري محلي وأي بروتوكولات مؤسسية.
- الموافقة الأخلاقية/القانونية وأي متطلبات لحماية المعطيات.

## 10. توصية الجلسة القادمة

الخطوة الأعلى قيمة الآن ليست ميزة جديدة، بل **إغلاق حلقة المراجعة**: يبدأ الطبيب
بمراجعة أول 5 حالات عالية الخطورة (ACS، الانسداد الرئوي، الإنتان، السكتة، التأق)،
لأن غياب التوقيع الطبي يبقي الأدوية محجوبة وكل المحتوى غير معتمد. تقنياً، تُنفّذ
البنية التقنية لـP1–P4 منفذة كعقود ومخططات فارغة، مع إبقاء المحرك والأوزان دون
تغيير. الخطوة التالية بعد وصول المحتوى: مراجعته وتوقيعه، ثم تعبئة السجل خلف أعلام
معطلة، ثم اختبار انحدار قبل أي تفعيل. لا تُترجم النصوص السريرية آلياً.

## 11. البنية المستقبلية المنفذة (تقنية فقط)

أُضيفت عقود ومخططات تحقق لما سيأتي لاحقاً، **بلا أي محتوى طبي أو قاعدة قرار**:

- `shared/future-content.ts`: أنواع الحوكمة (`ReviewAttestation`, `GovernedReference`)،
  أفعال P1–P4 كحاويات ترتيب فقط (`priorityDefinition: pending_medical_definition`)،
  المسارات (`PathwayNode`)، تفسير التحاليل، مغلفات سلامة الأدوية، الفئات السكانية،
  والتصدير/الطباعة/العمل دون اتصال.
- `server/governance/future-schemas.ts`: مخططات Zod صارمة، تحقق من الهوية الفريدة،
  وسلامة المراجع والمسارات. أي محتوى `approved` بلا مراجع/تاريخ/وثيقة مصدر يُرفض.
- السجل `FUTURE_CONTENT_REGISTRY` فارغ بالكامل، وكل `FUTURE_FEATURE_FLAGS = false`،
  والعمل دون اتصال `storage: 'none'` مع منع معرّفات المرضى في التصدير.
- `GET /api/capabilities` يعيد حالة `pending_medical_content` وأعداد الوحدات (كلها
  صفر) والأعلام (كلها معطلة)؛ لا يعيد أي محتوى سريري.

هذه بنية مؤجلة: لا واجهة تفعّل P1–P4، ولا مسار تكيفي، ولا تفسير تحاليل، ولا بيانات
أدوية جديدة. تعريف P1–P4 السريري وترتيبها ومدلولاتها **ما زال بانتظار الطبيبة**.

## 12. فحص حزمة GitHub Pages وحدود الإخفاء

الفحص الفعلي بعد `npm run build:pages`:

- الحزمة `dist/pages/assets/static-engine-*.js` تحتوي بيانات قاعدة المعرفة كاملة،
  ومنها اسم دواء مثل `Aspirin` (ظهر مرتين في النسخة المفحوصة).
- لذلك: **الواجهة لا تعرض الأدوية**، و**الـ API يعيد `medications: []`**، لكن البيانات
  الأصلية موجودة داخل ملف JavaScript عام قابل للتنزيل. لا يصح القول إنها «مخفية»
  أو «غير قابلة للوصول» تقنياً في نسخة GitHub Pages.
- أسماء الحالات الفرنسية القديمة أُزيلت من الحزمة بعد تطبيق سياسة العربية فقط.

الخيارات إذا كان المطلوب منع الوصول إلى البيانات نفسها:

1. **إزالة وقت البناء:** إضافة خطوة Vite تحذف `actions.medications` من نسخة الصفحات
   الثابتة. تخفف تسريب الأدوية فقط، وتبقي بقية المحتوى السريري عاماً.
2. **فصل معماري:** إبقاء المحرك والبيانات على خادم خاص والاكتفاء بواجهة عامة تستدعي
   API. يمنع تنزيل القاعدة كاملة، لكنه يلغي الاستقلال الكامل لنسخة GitHub Pages ويحتاج
   استضافة ومصادقة/تفويض.
3. **تشفير أو تعمية الحزمة:** لا يمنع الوصول الفعلي لأن المفتاح سيكون في العميل؛ غير
   مناسب كحماية.

**القرار المعتمد في هذه المرحلة:** تبقى البيانات كما هي داخل الحزمة الثابتة، ولا
يُحذف الكود ولا يُنقل المحرك إلى خادم خارجي. الواجهة والـ API يستمران في حجب
`actions.medications`، وتُبقي البيانات الأصلية للمراجعة الطبية والتحرير والاعتماد
لاحقاً.

**الحدّ المقبول صراحةً:** الوضع الحالي يلبي «عدم العرض كتوصية غير مراجعة»، ولا يدّعي
«سرية قاعدة المعرفة» أو منع تنزيل بياناتها من الحزمة العامة. إعادة النظر في الخيار 1
أو 2 مؤجلة إلى ما بعد المراجعة الطبية، ولا تُنفّذ دون طلب صريح.
